# implement_20260816_095318.md

작성 일시: `2026-08-16 09:53:18 KST`

**게임별 UI 아트 디렉션**을 파이프라인의 정식 단계로 만든다. 사용자 지적 "개발 내용이 이전
개발이랑 디자인 완전 동일해"에 대한 근본 대응(선택지 B)이다.

## 문제 — 측정된 사실

`keeper-last-light`와 `last-minute-keeper`의 동일도:

| 파일 | 동일도 |
|---|---|
| `LayoutRegistry.js` · `AudioManager.js` · `MobileButton.js` · `SaveData.js` | **100%** |
| `theme.js` | 82% (색만 교체) |
| `GameOverScene.js` | 88% |
| `PauseScene.js` | 67% |
| `LoadingScene.js` | 62% |
| `HomeScene.js` | 59% |

홈 화면의 세로 배치 사다리가 거의 겹친다: `0.16/0.15 · 0.225/0.215 · 0.335/0.345 · 0.505/0.485`.
글자와 배경 사진만 바뀌고 위치·크기·색 역할이 그대로다.

**중요한 단서**: 기존 v2 게임 3개(`firebreak-commander`, `ghost-train-railgun`,
`skybreak-gunship`)는 서로 다르다 — 홈 씬 줄 수도 버튼 수도 배치도 제각각이다.
**즉 스캐폴드가 아니라 작성자(에이전트)의 반복 습관이 원인이다.** 그러므로 수정은
스캐폴드가 아니라 **스킬이 지시하는 작업 순서**를 겨냥해야 한다.

## 근본 원인

계약은 **"무엇이 있어야 하는가"**를 정한다 — 목표 문구, 시작 버튼, 일시정지, 진행 지표,
버튼 크기 토큰. 그런데 구현자가 그것을 **"어떻게 보여야 하는가"**로 굳혔다. 목표를 5줄
가운데 정렬로 쓰라고 한 규칙은 어디에도 없는데 두 번 다 그렇게 했다.

그리고 파이프라인 어디에도 **게임마다 UI 정체성을 다르게 만들라는 요구가 없다.** 아트
프롬프트에는 스타일 가이드가 있지만 UI 레이아웃·타이포·구성에 대한 아트 디렉션 단계가 없다.
그래서 아트는 게임마다 다른데 UI는 같은 앱처럼 보인다.

## 개발 목적

- 게임마다 **UI 아트 디렉션을 데이터로 선언**하게 하고, 런타임이 그것을 실제로 읽게 한다
  (선언이 장식이 되지 않도록).
- **규격(uniform)과 표현(distinct)의 경계를 계약에 명시**한다. 버튼 크기·첫 플레이 요소·
  레이아웃 레지스트리는 같아야 하고, 배치·형태·타이포·모션은 달라야 한다.
- **기계 검사**를 붙인다. 미적 판단은 못 하지만 "두 게임의 선언이 같은가", "홈 배치 사다리가
  기존 게임과 겹치는가"는 잴 수 있다. 이번에 실제로 일어난 실패가 정확히 그 형태였다.
- 스킬(`game-factory`)에 **씬 구현 전 UI 디렉션을 먼저 정하는 단계**를 넣는다.
- `last-minute-keeper`의 UI를 자기 디렉션대로 다시 디자인해 단계가 실제로 작동함을 증명한다.

## 설계

### 선언 — `src/game/config/uiDirection.js`

런타임이 실제로 읽는 파일이다. 씬이 이 값을 참조해 배치·형태를 결정하므로, 선언과 화면이
어긋날 수 없다.

```js
export const UI_DIRECTION = Object.freeze({
  // 이 게임의 HUD가 흉내 내는 실제 사물. 레이아웃 은유의 출발점이다.
  layoutMetaphor: 'stadium-scoreboard',
  // 홈 화면 구성 방식. 'centered-stack'은 이미 두 게임이 썼으므로 재사용 금지.
  homeComposition: 'left-rail-lineup',
  // 버튼 형태 언어. 크기는 §2.0.25 토큰이 정하고, 형태만 게임이 정한다.
  buttonForm: 'jersey-number-plate',
  // 타이포 위계 — 표시용 글꼴 역할과 대비 방식
  typeScale: 'condensed-display',
  // 등장·퇴장 모션 서명
  motionSignature: 'slide-from-touchline',
});
```

### 검사 — `scripts/check_ui_direction.mjs`

미적 판단은 하지 않는다. 세 가지만 본다.

1. **존재**: v2 custom-loop 게임에 `uiDirection.js`가 있는가
2. **충돌**: `layoutMetaphor` · `homeComposition` · `buttonForm` 세 값의 조합이 다른 게임과 같은가
3. **배치 사다리 중복**: 홈 씬의 `height * 0.xx` 값 집합이 다른 게임과 **±0.02 이내로 3개 이상**
   일치하는가 — 이번에 실제로 일어난 실패의 기계적 서명이다

### 계약 §2.0.26 — 규격과 표현의 경계

| 같아야 하는 것 (규격) | 달라야 하는 것 (표현) |
|---|---|
| 버튼 크기 토큰(§2.0.25) | 버튼 형태·테두리·라벨 처리 |
| 첫 플레이 5요소의 **존재** | 그 5요소의 **배치와 표현** |
| Layout Registry required ID | 화면 구성·정렬·여백 리듬 |
| 일시정지·도움말의 **동작** | 오버레이의 생김새 |
| DPR·안전영역 규칙 | 타이포 위계·모션 |

### 재디자인 중 드러난 별개 결함 — QA 어댑터의 배치 결합

홈을 팀 시트 행 구성으로 바꾸자 **내용은 그대로인데** 어댑터 3종이 죽었다. 원인은 모두
"검사가 배치에 결합돼 있었다"는 한 가지다.

| 증상 | 원인 | 조치 |
|---|---|---|
| `first-play-clarity` 4개 항목 실패 | 특정 텍스트 객체(`scene.goal.text`)를 긁고 있었다 | 씬이 `firstPlayCopy`를 공표하고 어댑터는 그것을 읽는다 |
| `lifecycle-soak` 15초 타임아웃 | GameOver 복귀 클릭이 `play.y + 85 * 3` 좌표 추정이었다 | `clickId('home')` — id로 부르니 의도까지 드러났다(원래 노린 것은 RETRY가 아니라 HOME) |
| `hostile-input` "registry has no id play" | 연타 검사는 전환 **후에도 같은 지점**을 눌러야 한다 | `locateId()`로 위치를 먼저 확정하고 `clickPoint()`로 연타 |

부수적으로 고친 것:

- `captured-state-qa.mjs` 러너에 `clickId` 주입 — 프로젝트 드라이버가 좌표 상수를 들지 않도록.
- 레지스트리 `x,y`는 `getBounds()` 기준 **좌상단**이다. 중심으로 보정하지 않으면 버튼 모서리를
  눌러 조용히 빗나가고, 다음 씬 대기가 타임아웃으로 죽는다.
- `scene-composite-qa`의 씬 대기 상한 6초 → 15초(저장소의 다른 어댑터와 정렬). 단독 3뷰포트
  2회 연속 통과인데 전체 게이트에서만 실패하는 헛불이 있었다.
- 씬 대기 실패 메시지에 기대 씬과 실제 씬을 담았다. 이전에는 `Timeout exceeded`만 나와서
  어느 전환에서 멈췄는지 알 수 없었고, 전체 게이트를 반복 실행하며 찾아야 했다.

이 규칙은 계약 **§4.1.1 "QA 어댑터는 좌표를 추측하지 않는다"**로 승격했다. §2.0.26과 같은
원칙이다 — 검사는 요소의 **존재**를 보고 **배치**를 보지 않는다.

- 선언 어휘(`layoutMetaphor` 등)가 늘어나면 관리 비용이 생긴다. 자유 문자열로 두되 충돌만
  검사해 어휘 사전을 만들지 않는다.
- `last-minute-keeper`의 게임플레이 결함(슈터 공중부양·원근 역전)은 이 계획 범위 밖이다.
  UI 재디자인과 섞으면 원인 추적이 어려워지므로 다음 워크스트림에서 따로 처리한다.
