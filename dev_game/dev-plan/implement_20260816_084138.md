# implement_20260816_084138.md

작성 일시: `2026-08-16 08:41:38 KST`

축구 골키퍼 게임 **「최후의 1분」(Last Minute Keeper, `last-minute-keeper`)** 제작 계획.

## 개발 목적

사용자 요구는 두 가지다: **축구 골 막기 주제**, 그리고 **"더욱 인터랙티브하고 정적이지 않게"**.
두 번째가 이 계획의 설계 제약이다. 직전 게임(`keeper-last-light`)이 왜 정적이었는지 원인을
특정하고, 그 넷을 구조적으로 뒤집는 것이 목표다.

| 직전 게임이 정적이었던 원인 | 이 게임에서 뒤집는 방법 |
|---|---|
| 배가 제자리에 **서서 기다렸다** — 화면이 멈춰 있는 시간이 대부분 | 공이 **항상 날아오고 있다**. 정지 프레임을 설계에서 배제한다 |
| 입력이 **버튼 하나** — 공간·위치 개념이 없었다 | **연속 드래그**로 키퍼를 움직인다. 매 순간의 위치가 결과를 바꾼다 |
| 물리가 없고 **판정 함수**였다 | 실제 **충돌·반사**. 쳐낸 공이 살아서 다음 위협이 된다 |
| 실패해도 화면이 변하지 않았다(게이지만 감소) | 실점하면 **네트가 출렁이고 카메라가 흔들리며 관중이 반응**한다 |

부차 목적: 직전 세 번의 후보정에서 배운 것을 **처음부터** 설계에 넣는다(§공통 진행 규칙).

## 왜 리스킨이 아닌가

기존 18개는 전부 **내가 쏘거나 배치해서 목표를 처리하는** 구조다(사격·궁술 9, 레이싱 2,
물류·지휘 3, 조리 1, 회피 1, 전략 1, 신호 1). **날아오는 것을 몸으로 막는** 축은 없다.
`meteor-dash`는 피하는 것이지 막는 것이 아니고, `harbor-crane-commander`의 물리는 내가 든
화물을 안정시키는 것이지 외부 위협을 인터셉트하는 것이 아니다.

이 게임의 정체성 축은 **예측 → 커밋 → 회복**이다. 읽고, 몸을 던지고, 그 대가로 잠깐 움직이지
못한다. schema v1 어휘(낙하 hazard + collectible + 좌우 이동)로는 다이빙 커밋도, 리바운드도,
굴절도 표현할 수 없으므로 **v2 custom-loop가 유일한 경로**다.

## 게임 설계

### 화면 구성 (세로 1170×2532)

```
상단 0.00~0.30   필드·공격수·관중   ← 슈터 백스윙에서 방향을 읽는 구간
중단 0.30~0.72   비행 구간           ← 커브·굴절·높이(그림자)가 보이는 구간
하단 0.72~1.00   골대 + 골키퍼       ← 엄지 사정거리 = 조작 구역
```

골대를 **아래**에 두는 것이 핵심 결정이다. 키퍼가 엄지 근처라 연속 드래그가 자연스럽고,
공이 위에서 내려오므로 궤적을 읽을 거리가 화면 세로 전체가 된다.

### 조작 — 두 층

| 입력 | 동작 | 대가 |
|---|---|---|
| **드래그(느림)** | 키퍼가 골라인을 좌우 이동. **최고 속도와 관성**이 있어 순간이동 불가 | 없음 |
| **플릭(빠름)** | 그 방향으로 **다이빙** — 도달 범위 2배 | 성공·실패 무관하게 **회복 시간** 동안 이동 불가 |

두 층이 매 슛마다 진짜 선택을 만든다: *따라가서 막을 수 있나, 지금 던져야 하나?*
다이브 남발은 리바운드에 당하고, 아끼면 구석을 못 막는다.

구분 방식: 포인터 이동 속도가 `diveFlickSpeed` 임계를 넘으면 다이브. 다이브 중에는 드래그
입력을 무시한다(회복 시간의 대가가 실질적이어야 한다).

### 정적이 되지 않게 만드는 장치 4가지

1. **리바운드가 살아 있다** — 쳐낸 공은 사라지지 않고 굴러다니다 다시 슛으로 이어진다.
   세이브 직후가 가장 위험한 순간이 되어, "막았다 → 대기"의 빈 시간이 사라진다.
2. **공이 휜다** — 마그누스 효과로 궤적이 곡선. 초반 방향만 보고 던지면 속는다.
   반응이 아니라 **예측**이 된다.
3. **굴절** — 수비수 다리에 맞고 방향이 바뀐다. 완벽한 예측을 무효화해 매 슛이 다르다.
4. **슛 종류가 다르다** — 강슛(빠름·직선) / 로빙(느림·머리 위) / 감아차기(느림·큰 커브) /
   헤딩(코너킥에서 갑자기). 종류마다 대응이 달라 근육 기억이 통하지 않는다.

### 스테이지 — 숫자가 아니라 상황이 바뀐다

| # | 상황 | 새로 생기는 것 | 배경 |
|---|---|---|---|
| 1 | 슈팅 연습 | 강슛·로빙 | 낮 훈련장 |
| 2 | 프리킥 | 벽 너머 **감아차기** | 석양 |
| 3 | 코너킥 혼전 | **헤딩 + 리바운드 다발** | 야간 조명 |
| 4 | 페널티 | 1:1, 느린 백스윙 = 심리전 | 정적인 밤 |
| 5 | 추가시간 | 전부 섞여 몰아침 | 폭우 |

### 규칙

- **패배**: 실점 5회
- **승리**: 스테이지 5(추가시간) 종료까지 버티기
- **점수**: 세이브 종류별 차등(캐치 > 펀칭 > 다리막기), 연속 세이브 콤보, 무실점 스테이지 보너스
- **난이도 축**: 경과 시간과 스테이지 인덱스만 참조. 남은 실점 여유·점수·콤보는 난이도에
  절대 넣지 않는다(결함 클래스 D).

### 계약 정합 설계 (결함 클래스 사전 차단)

- **B (시각 단일성)**: 골대 프레임·잔디·관중·조명탑은 **배경 소유**. 공·키퍼·수비수·FX만
  런타임 소유. 배경 프롬프트에 "no ball, no goalkeeper, no players in the goal mouth" 명시.
- **C (UI/게임플레이 분리)**: 스코어보드·다이브 게이지는 화면 상·하단 고정 UI 층(depth 20+),
  게임플레이는 depth 10~19. 화면의 모든 도형은 의도된 렌더로 문서화한다.
- **E (진행 완결성)**: 스테이지마다 (목표 시간, 보상, 다음 상태)를 config 데이터로 선언하고
  승리·패배 양쪽 터미널을 모두 도달 가능하게 한다.
- **M (물리 경계)**: 키퍼의 **판정 body와 보이는 스프라이트**를 일치시킨다. 다이브 중에는
  body가 늘어나므로 그 상태의 body도 캡처로 검증한다.
- **H/I/J/K**: BGM 단일 핸들, 전환 버튼 one-shot, 저장 복구, 씬 shutdown 정리.

### 첫 플레이 이해도 (클래스 N)

목표(추가시간까지 버티기) · 승리 · 패배(실점 5) · 첫 행동(드래그로 이동, 빠르게 튕기면
다이빙) · 진행 지표(스테이지 / 실점 / 세이브 수) · 도움말 정지·재호출을 홈과 도움말에 선언한다.

## 공통 진행 규칙 — 직전 세 번의 후보정에서 배운 것을 선반영

이 절이 이 계획의 핵심이다. 아래는 전부 `keeper-last-light`에서 **게이트가 GREEN인 채로
사용자에게 발견된** 결함들이다. 같은 것을 다시 만들지 않는다.

1. **UI 프레임은 처음부터 9-slice.** `setDisplaySize`로 원본 비율을 깨뜨리지 않는다.
   (실측 사례: 2.00:1 자산을 4.54:1로 늘려 테두리가 좌우만 1.47배 두꺼워지고 베벨이 뭉갬)
2. **스프라이트별 투명 여백을 실측해 config에 넣는다.** 스프라이트 경계로 UI를 붙이면
   자산마다 다른 높이에 뜬다(실측: 여백 5~28%로 제각각).
3. **배경의 지평선/지면 위치를 확인하고 게임플레이 좌표를 잡는다.** 화면 비율로만 잡으면
   오브젝트가 공중부양한다.
4. **배치 슬롯은 점유 여부로 배정한다.** 순번의 나머지 연산은 겹침을 만든다.
5. **오디오는 처음부터 44.1kHz + 어택/릴리즈 엔벨로프 + 배음.** 순수 사인파와 저샘플레이트는
   "품질이 낮다"는 지적으로 직결된다. BGM은 지연 로드하되 루프 이음매를 크로스페이드한다.
6. **패널 안 텍스트는 스프라이트가 아니라 안쪽 필드 기준으로 배치하고, 보이는 행 수에 따라
   동적으로 정렬한다.** 비어 있는 행이 자리를 차지하면 내용이 한쪽으로 쏠린다.
7. **캡처는 실제 도달 가능한 상태만 담는다.** 디버그 훅이 동시 등장 상한을 넘기거나 임의
   입력으로 오답을 만들면, 실제 플레이에 없는 화면이 증거로 남는다.
8. **아트는 백그라운드 실행 + `--skip-existing` 재개.** 단일 명령 타임아웃을 넘는 것이 정상이다.
9. 아트 단계 전에 `factory:host-preflight`로 생성 가능 여부를 판정한다.
10. 게이트 실패는 **production-demo 미통과**로 보고하고 완료로 부르지 않는다.

## QA 관점

- [ ] **정적이지 않은가** — 게임플레이 캡처에 항상 움직이는 공이 있는가. 공 없는 정지
      상태가 1초 이상 지속되는 구간이 있는가(있으면 설계 실패).
- [ ] 드래그와 플릭이 명확히 구분되는가 — 느린 드래그가 다이브를 유발하지 않고, 빠른 플릭이
      이동으로 오인되지 않는가.
- [ ] 다이브 회복 시간이 실제로 대가로 작동하는가 — 회복 중 입력이 무시되는가.
- [ ] 리바운드가 살아나 다음 위협이 되는가 — 세이브 직후 공이 사라지지 않는가.
- [ ] 키퍼의 판정 body가 보이는 스프라이트와 일치하는가(**다이브 상태 포함**) — 클래스 M.
- [ ] 골대·잔디가 배경 소유이고 런타임이 중복 렌더하지 않는가 — 클래스 B.
- [ ] 공의 높이(로빙)가 그림자로 읽히는가 — 원근 없이 높이를 판별할 수 있는가.
- [ ] 오디오 실측: 샘플레이트 ≥ 44100 / **원샷 SFX**는 피크 ≥ 0.75 · 시작·끝 진폭 < 0.01 /
      **루프 BGM**은 이음매 불연속 < 0.005 · 시작 진폭 < 0.01(영점 교차로 회전시켜 달성).
      루프에 원샷 기준을 그대로 적용하면 안 된다 — 루프는 파형 중간에서 시작하는 것이 정상이고,
      중요한 것은 끝과 앞이 이어지는가다.
- [ ] UI 프레임이 9-slice이고 표시 테두리가 사방 ±1 CSS 이내인가.
- [ ] `custom-loop-full-qa` 8종 전부 통과하는가.
- [ ] backingScale ≥ min(dpr, 3) — 논리 캔버스가 390×844의 3배수(1170×2532)인가.

## 성공 판정

이 계획은 게이트 통과만으로 성공이 아니다. **"정적이지 않다"**는 사용자 요구가 충족되어야 한다.
판정 기준: 게임플레이 캡처 전부에 움직이는 공이 있고, 공 없는 정지 상태가 1초 이상 지속되는
구간이 설계상 존재하지 않으며, 세이브 직후가 다음 위협으로 곧장 이어진다.
