## 문제 — 측정된 사실

### ① 슈터 공중부양

`GameScene.js:42`가 슈터를 `height * 0.20`에 놓는다. 배경 5장의 지평선을 실측하면:

| 배경 | 지평선(잔디 시작) |
|---|---|
| stage-1 | ≈ 0.28 |
| stage-2 | ≈ 0.48 |
| stage-3 | ≈ 0.47 |
| stage-4 | ≈ 0.49 |
| stage-5 | ≈ 0.44 |

**0.20은 다섯 장 모두에서 하늘 또는 관중석이다.** 공 발사점 `height * 0.26`(`GameScene.js:193`)도
마찬가지다. 슈터 크기 `150 * unit`(캔버스 폭의 38%)도 먼 거리의 인물로는 과하다.

### ② 원근 역전

`BallPhysics.ballVisuals()`:

```js
scale: 1 + ball.height * 0.55,
```

카메라는 골대 뒤에서 필드를 올려다본다(캡처 확인 — 키퍼의 등이 보이고 골대가 화면 아래
전경에 크게 그려진다). 따라서 공은 **다가올수록 커져야** 한다. 그런데 스케일이 거리가 아니라
아크 높이에 묶여 있어서:

- 평평한 강슛(`height: 0.18`)은 비행 내내 크기가 거의 변하지 않는다 — 다가오는 느낌이 없다.
- 로빙(`height: 0.86`)은 **중간에 가장 크고 도착할 때 작아진다** — 원근이 뒤집힌다.

그림자도 뒤집혀 있다. `Ball.sync()`는 공을 `ball.y`에, 그림자를 `ball.y + offset`에 그린다.
높은 공일수록 그림자가 공보다 **앞(아래)** 으로 나가므로 공이 지면보다 낮게 읽힌다.

### ③ 비행 회랑이 관중석을 가로지른다

0.26 → 0.913 구간의 위쪽 절반이 하늘·관중석이다. 공이 잔디 밖에서 날아온다.

## 개발 목적

- 슈터와 발사점을 **잔디 위**로 내리고, 원근에 맞는 크기로 만든다.
- 공의 크기·그림자를 **거리(progress)** 에 연동해 다가오는 느낌을 복원한다.
- 회랑이 짧아지는 만큼 속도를 재조정해 **비행 시간을 보존**한다. 텔레그래프 창(260~700ms)과
  다이브 회복(620ms)이 반응 시간 기준으로 조율돼 있어, 시간이 바뀌면 난이도가 통째로 바뀐다.

## 설계

### 균일 발사선을 쓰는 이유

지평선이 0.28~0.49로 벌어지므로 스테이지마다 슈터를 지평선 바로 아래에 놓으면 회랑 길이가
스테이지마다 40%까지 달라진다 — 같은 슛 종류가 스테이지마다 다른 시간에 도착한다는 뜻이라
난이도가 통제 불능이 된다.

그래서 **모든 지평선보다 아래**인 단일 발사선을 쓴다. 가장 깊은 지평선이 stage-4의 0.49이므로
`SHOOTER_LINE = 0.52`면 다섯 장 모두에서 잔디 위다. 슈터가 스테이지마다 원근상 다른 깊이에
서는 것처럼 보이지만, 슈팅 연습에서 사수가 같은 거리에 서는 것은 자연스럽다.

### 원근 모델

```
persp(progress) = FAR + (1 - FAR) * progress      // FAR ≈ 0.45, 발사 시 45% 크기
scale  = persp
lift   = height * CROSSBAR_LIFT * persp           // 높이를 화면 위로 들어 올린다
공 스프라이트 y = groundY - lift
그림자        y = groundY                          // 그림자는 항상 지면에
```

`ball.y`를 **지면 위 발자국**으로 정의하고 공을 그 위로 들어 올린다. 지금은 반대라서 그림자가
공보다 앞으로 나간다.

`CROSSBAR_LIFT`는 도착 시점에 `height=1`이면 크로스바 높이에 오도록 잡는다. 골라인 0.913,
크로스바 실측 ≈ 0.62 → 0.29 캔버스 높이.

### 속도 재조정

회랑: `0.913 - 0.26 = 0.653` → `0.913 - 0.52 = 0.393`. 비율 **0.602**.

| 슛 | 기존 speed | 신규 speed | 비행 시간(보존) |
|---|---|---|---|
| drive | 1750 | 1053 | 0.945 s |
| lob | 1000 | 602 | 1.654 s |
| bender | 1180 | 710 | 1.402 s |
| header | 1450 | 873 | 1.141 s |

`vx` 역산은 `flightSec` 기준이라 곡률 상수는 그대로 두어도 같은 궤적을 그린다.

### 부수적으로 드러난 두 가지

**① 그림자 불투명도가 이중으로 곱해지고 있었다.** `add.ellipse(..., 0x000000, 0.35)`의 채우기
알파와 `setAlpha(0.12~0.42)`가 곱해져 실효 4~15%였다. 채우기를 1로 두고 불투명도를
`ballVisuals` 하나가 소유하게 했다.

**② 디버그 훅 `forceShot`이 실제 발사와 다른 인자로 공을 쏘고 있었다.** `crossbarLiftPx`가
빠져 리프트가 NaN이 됐다. 캡처 증거가 실제 플레이와 다른 상태를 찍는다는 뜻이라, 그 증거로
통과 판정을 내리면 안 된다. 인자를 실제 발사와 동일하게 맞췄다.

### 계측 방법에서 배운 것

그림자를 "렌더되지 않는다"고 두 번 오판했다. 원인은 `page.evaluate`로 좌표를 읽고
`page.screenshot`을 찍는 사이에 공이 **60px 움직였기** 때문이다. 그림자 높이가 5 CSS px라
그 정도 어긋나면 완전히 다른 행을 재게 된다. 씬을 멈춰 계측과 캡처를 같은 프레임에 묶고
나서야 +21~+85/255가 나왔다.

교훈은 계약 §4.1.1과 같은 종류다 — **움직이는 것을 잴 때는 계측과 증거가 같은 프레임에서
나와야 한다.** 아니면 없는 결함을 만들어내고, 그것을 근거로 코드를 고치게 된다.
